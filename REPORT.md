# CS TeamUp — Standards 1.8.4 Report

## Scope

This revision upgrades CS TeamUp from the previous subsystem scaffold to **CSMJU2030 Standards 1.8.4**.
The product domain from the original prototype is retained: project discovery, recommendations, project creation/editing/deletion, applications, invitations, membership, Q&A, follows, reviews, messaging, notifications, profile and portfolio references.

## Architecture

- Frontend: Next.js App Router 16.3.6 + React 19.2.8 + Tailwind CSS v4.
- Shared transition UI is copied from `standards/templates/csmju-subsystem-web/src/csmju`; it is not forked into `components/ui`.
- Backend: NestJS 11.
- Database: PostgreSQL 16 with Prisma 7.9.1 and `@prisma/adapter-pg`.
- Frontend is the only public origin and proxies `/api/*` and `/auth/*` to backend.
- Identity is `core_user_id` from Core Hub JWT `sub`; TeamUp does not create a local user/account table.

## Security / Auth

- Core Hub SSO endpoints exist at `/auth/login`, `/auth/callback`, `/auth/logout`.
- Access token is accepted from Authorization Bearer or the subsystem HttpOnly cookie, with Bearer taking precedence.
- JWT verification uses RS256 + JWKS + `kid`, issuer, audience, required claims, lifetime limit and `azp` validation.
- JWKS caching/cooldown is configured.
- No login form and no token in browser storage.
- Callback state is one-use, constant-time compared, expires within 600 seconds, and invalid browser callbacks return a 401 re-login page without creating a session cookie.

## API / Data

- Global API prefix is `/api`; business routes are `/api/v1/*`; health is `/api/health`.
- Response envelope is applied centrally.
- DTO validation uses `ValidationPipe` with whitelist/transform/forbidNonWhitelisted.
- UUID path parameters use UUID v4 validation.
- Database identifiers and columns follow the required snake_case mapping.
- Project membership acceptance uses a database row lock to prevent overfilling the team in concurrent requests.

## UI

All app routes are under the standard `CsmjuAppShell`. Standard `PageHeader`, `Tabs`, `StatusBadge`, `Modal`, `ConfirmDeleteModal` and tokenized UI classes are used. The main Projects page has visible labels, loading/error/empty states, responsive cards and filter tabs. Static previews are included at `docs/ui-preview.png` / `docs/ui-preview-mobile.png`, and `/preview` in the frontend uses the real standard UI components for an interactive visual example.

## Deployment

- `.standards-version` = `1.8.4` and the included standards snapshot is the 1.8.4 source used for this package.
- Root build context is used by both Dockerfiles.
- API container exposes 4000 and web container 3000 internally.
- Final Docker stages run as non-root `node`.
- Root `.dockerignore` excludes env files, node_modules and build output.
- Compose includes `db`, `api`, `web`, read-only runtime, dropped Linux capabilities, `no-new-privileges`, tmpfs, memory limits and rotated logs.

## Verification status

Static checks were run with the bundled 1.8.4 scripts after the revision. All deterministic checks completed successfully. `GH-01` reports the expected environment-only failure because the working copy is not a real Git branch/PR context. Dependency installation, application build, unit tests and runtime conformance were not executable in the build environment because it had no network access to the npm registry and no pnpm installation/cache. Therefore this report does **not** claim a real `next build`, `nest build`, `pnpm test` or L3 runtime conformance pass.

`pnpm-lock.yaml` is intentionally not hand-authored because this build environment has no registry access. It must be generated by pnpm 12.3.4 in a network-enabled development/CI environment and committed before merge.
